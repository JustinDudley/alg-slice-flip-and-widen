README

This app generates algs for my no-parity-pochmann Rubik's Cube system. See my YouTube video, XOXOXOXOXOXOXOXOXO. It takes as input a list of face-turn-only algs, and gives as output a much longer list of algs with wide turns and slices.

To run the program: Select a file from library_of_input_algs. Copy-paste the algs into INPUT_file/alg_list_StickerSolve_input.txt.  Run the program from main, and then open the newly generated output file.

This single README will serve well enough for all 4 branches of the repo: a, b, c, d.  It really only explains the "a" branch. My apologies for any confusion…

Notation for whole-cube rotations: I have used capital X, Y, Z.  My bad.

I HAVE NOT USED STANDARD SLICE NOTATION.  You can read why here: https://rebrand.ly/greatest-hits-eb84dd.  Instead of E,M,S,  I use H,T,S, like so:  H = E', T = M', S = S.

My input algs were all generated by the StickerSolve desktop app, which was created by TAR-ALEX. StickerSolve did all the heavy lifting, all the math. This Python program, using string manipulation informed by knowledge of the cube, then takes each StickerSolve alg and uses it to generate many more wide-turn algs, resulting in about a 200-fold increase.

Special Note just for branch "c":
skis__not__tees refers to an alg that has a slice complement such as U D'.  I call such a turn-pair "skis". In this branch, all StickerSolve algs EXCEPT those having exactly ONE skis instance are discarded. And then the skis are intentionally NOT compoundified. So there are no T's ("no tees"), and and no S's, and no H's (no M's, S's, or E's in standard slice notation). As Y or Z ripples left, i ONLY capture the moment where the Y or Z is in the middle of the skis. This turns the formerly parallel skis into "snowplow" skis:  U D' Z becomes U Z L'   as Z ripples left and into the pair. The two skis, formerly paralleL, are now at right angles, with a WCR between them.     Then I run itertools to generate all the r and l possibilities. That's it. It's a small group of algs that are generated. But I believe it will generate a few very short edge algs with no slice turns.
----------- ---------- -----------
No-parity-pochmann algs are designed to swap 3 pairs of center stickers, and either one pair of edges OR one pair of corners.  They do THIS sort of thing:
U r U' R2 D F' R' F U r U' R' F' l d (x) D' R2

I used StickerSolve to generate a set of base algs. The app is AMAZING -- But I had trouble getting reliable results when I asked it to use slices and wide turns. So I asked StickerSolve to do THIS sort of thing (using face turns only):
U2 F U' D' R' F B R2 D' R2 U D' L2 D' R' L' B D2. 
…with the implication that I would add a (Z' X2) "tag" myself at the end of the alg to "put it right".  

So our complete DEMO ALG is now:
U2 F U' D' R' F B R2 D' R2 U D' L2 D' R' L' B D2 (Z' X2) 

I generated many long lists of algs using StickerSolve. They are the inputs to this program.

The app decides which of 6 "tags" a StickerSolve alg needs in order to be "put right".  No-parity-pochmann algs must turn the cube's core 90 degrees in one direction and 180 degrees in one of the other two directions. Here are the 6 geometrically possible options, which I call the "odd swap" options. Each can be "spelled" in 4 different ways using different whole-cube rotations. But only 8 of the resultant 24 end with an X component, and those are the ones I required:   Y' X2,  Y X2,  Z X2,  Z' X2,  Y2 X'==Z2 X,  Y2 X==Z2 X'. 

A pair of tags with "==" between them do the same thing to the cube. The fact that some of the algs require to be run twice, with two different tags from a pair, makes the code considerably denser. Also, the Y/Z component and the X component of the tag are handled differently from each other in the code.

It turns out that any alg, no matter how many Y, Z, or X turns it has within it, can be re-written in what I call "Alg--YorZ--X" format  [or, "Tipper Gore format" :)  ].  The "Alg" component has no whole-cube rotations. The YorZ component contains either a Y OR a Z but not both (could contain Z2…). And the X component is X, X', or X2. Any of the three components could also be blank/missing/empty. 

Back to the demo:  After receiving its tag, certain internal alg pairs are replaced by slices.  The U D' in our demo alg is replaced by H' Y   [E Y in standard slice notation]  to make:
U2 F U' D' R' F B R2 D' R2 (H' Y) L2 D' R' L' B D2 (Z' X2)

Then this new Y is moved to the end of the alg, which necessitates altering each non-Y-axis turn between the H' and the end of the alg. Here is the result. You may have to do some head scratching here…
U2 F U' D' R' F B R2 D' R2 (H') F2 D' B' F' L D2 (Y)  (Z' X2)

Any 3 or more whole-cube rotations can be reduced to 2 at most. The 3 at the end, in this case, reduce to (Z' X), yielding:
U2 F U' D' R' F B R2 D' R2 (H') F2 D' B' F' L D2 (Z' X)

Now the fun begins. That Z', the YorZ component, is going to be "rippled" through the whole alg, from right to left.  Here is what the first 7 results of that rippling look like:
(1)  U2 F U' D' R' F B R2 D' R2 H' F2 D' B' F' L D2 (Z')   (X)    (no rippling yet)
(2)  U2 F U' D' R' F B R2 D' R2 H' F2 D' B' F' L (Z') R2   (X)
(3)  U2 F U' D' R' F B R2 D' R2 H' F2 D' B' F' (Z') D R2   (X)
(4)  U2 F U' D' R' F B R2 D' R2 H' F2 D' B' (Z') F' D R2   (X)  (Trivial: B,Z,F order doesn't matter)
(5)  U2 F U' D' R' F B R2 D' R2 H' F2 D' (Z') B' F' D R2   (X)  (Trivial: B,Z,F order doesn't matter)
(6)  U2 F U' D' R' F B R2 D' R2 H' F2 (Z') R' B' F' D R2   (X)
(7)  U2 F U' D' R' F B R2 D' R2 H' (Z') F2 R' B' F' D R2   (X)  (Trivial: Z,F order doesn't matter)

Each of these is a legit, working alg.  And NOW each one gets subjected to the program's ITERTOOLS method to generate many OTHER legit algs.

Alg (7), by itself, is used by itertools to generate the following 8 algs, each of which now contains WIDE TURNS:
U2 F U' D' l' U D R2 F' R2 S Y' U2 R' D' U' F R2
U2 F U' D' R' F B R2 D' R2 H' Z' F2 l' D' U' F R2
U2 F U' D' l' U D l2 B' l2 S Y' U2 R' D' U' F R2
U2 F U' D' l' U D l2 B' R2 S' Y D2 R' U' D' B l2
U2 F U' D' l' U D R2 F' l2 S' Y D2 R' U' D' B l2
U2 F U' D' R' F B l2 U' l2 H' Z' F2 l' D' U' F R2
U2 F U' D' R' F B l2 U' R2 H Z B2 l' U' D' B l2
U2 F U' D' R' F B R2 D' l2 H Z B2 l' U' D' B l2

Here's the idea:  Every face turn has a complementary wide turn. R'--l', U--d, F2--b2… You can replace any single turn in an alg with its complement… as long as you then adjust every subsequent turn and put a whole-cube rotation at the end.  If you replace TWO turns in an alg, the resultant whole-cube rotations might cancel each other out -- especially if you do it cleverly. You could also replace 3 or more (for instance, replacing R', R', and R2 with l', l', l2). Many common algs, which contain an r, and then later an r', work on this principle.

But no one likes to do u,d,f,b turns, only r and l.  So itertools only looks to replace (with complementary wide turns) the turns in the X-family (R, R', R2, L, L', L2).    Alg (7) has 5 turns in the X-family, in this order:  R', R2, R2, R', R2.  Itertools could replace any two of the R2 turns and the alg would come out right. It could also replace one R2 and two of the R' turns.  EXCEPT:  Itertools has a second job, which is to get rid of the X component, in this case (X), that appears at the end of our demo alg. (The idea is that cubers would rather not have whole-cube rotations in their algs). So actually, itertools is going to examine every combination of singles, pairs, triples, quadruples, etc., of X-family turns, play out each scenario, and make any and all replacements that will end up turning the core of the cube in the direction of one X (or, to use my previous phraseology, "canceling out" the X).

So, when I call this repo "alg-slice-flip-and-widen", what that means is this:  The Python code will take an existing StickerSolve alg and, instead of just adding a simple tag such as (Z' X2) to flip the cube 90 degrees in one direction and 180 degrees in another, it will use X-family turns WITHIN the alg to flip the cube. First it replaces certain face-turn pairs with slices. Then it completes the job by finding EVERY combination of r, l, l2… wide turns that will do this flipping.

My original intention was to generate algs that BEGAN with either a Y or a Z, and then had no further whole-cube rotations. I ended up accepting Y or Z in the middle of the alg as an alternative, and some of my favorites are those that have a Y D pair (or Z' B', etc.) that truncate to a single u wide turn. These algs contain zero whole-cube rotations.

My goal (in branch "a") was to find EVERY POSSIBLE ALG IN EXISTENCE with the following constraints to its shape: 
  - No more than ONE whole-cube rotation (and always a Y or Z, never an X because X-axis turns are achieved through wide turns r and l)
  - OR, zero whole-cube rotations and no more than ONE wide turn in the group u,d,f,b.

An alg that rotates the core must do so in one of 3 ways: Slice, wide turn, or whole-cube rotation. In future iterations of this project I plan to be more accepting of whole-cube rotations as the best finger-friendly solution. 

Basically, I've just described branch "a" of the repo. Each branch has a different twist, and not all elements of the description above are present.

(Given the complexity of the job, you may begin to see why I can't tolerate standard slice notation. For me, it is just too difficult to think through the math with a notation that isn't self-consistent. It's a matter of necessity, not preference.) 

And by the way, finding all these complement substitutions is a great idea for ANY alg, regardless of whether you want to flip the cube or do anything with no-parity-pochmann. The programming could be (and should be, and presumably already HAS been in some form, by somebody) written without the flipping part, so that any alg in the world could generate 50 new algs. 

This repo goes hand-in-hand with its partner repo, filter-and-sort. The goal is to generate many algs, then search for a few that feel good for the hands to turn. In this project, the 4 branches of this app each took as input about 400,000 StickerSolve algs and together generated 93 million algs as output. These were then filtered down to 68,000 relatively finger-friendly algs by filter-and-sort.
